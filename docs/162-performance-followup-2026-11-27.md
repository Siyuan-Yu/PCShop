# 性能优先项续修与实测记录

## 当前结论

本轮承接用户“继续处理完”及上一轮实测验收要求，在 `art/experiment` 工作区继续修复。没有切换分支、打包、提交或上传，没有降低模型、材质、阴影、绿化质量。原有 Unity 编辑器及其导入进程保留。

**稳定 120 FPS 尚未验收通过。** 前一份 [161 验收报告](161-120fps-acceptance-2026-11-27.md) 中确认的 UI 周期峰值、NPC 寻路峰值、读档初始化、跨日人物池失效已分别处理；本轮继续记录剩余慢帧，不把平均 FPS 超过 120 当作完成。

## 修复内容

1. **寻路与客流初始化**：路网采用可复用的索引、数组和二叉堆，保持原有同分选路顺序；A* 路径缓存限制 2,048 项，FIFO 淘汰，新增节点或边时失效。商圈距离使用同一索引实现 Dijkstra；同一城市的静态客流地理计算在会话之间共享，不缓存经营收益、现金、竞争或通行权限。
2. **NPC 初始化和日常活动**：街头服务节点用门口空间索引检查净空，保留原来的距离排序与精确距离条件。外出计划在统一道路比例下，用保守的最短时间下界过滤明显无法及时到达的地点。通勤与最近节点缓存满额后只淘汰一项，避免一次全部清空造成尖峰。
3. **HUD**：静止时复用几何路线预览，现金、任务、通行条件实时判断；预览路线不会用于实际移动。低频 HUD 分四个时段更新，各项目仍约每 0.4 秒刷新一次，避免集中在同一帧。没有改变页面样式与功能。
4. **人物显示**：先过滤不可见的私人室内人物，再计算展示位置；已登记固定形象不再因午夜换日销毁人物池。动态角色只在真实衣着温度档变化时换装。加载界面逐人预备登记 NPC 的共享网格、坐姿形变和材质，再销毁临时人物，实际游戏的 NPC 数量与外观不变。
5. **计时与复现**：补充分段 CPU、Unity 引擎计时和慢帧记录。核心细分计时仅在诊断模式启用；正常巡检不启用每位 NPC 的采样回调。`Step` 的休息分帧分支也记录模拟、视图和 UI 时间。

## 回归口径

- 完整 JSON 比较：睡眠、昏倒、住院三个合成初始存档，优化后的全部存档字段与优化前结果逐字一致；并非只检查现金、日期或人物数量。合成数据与玩家存档隔离。
- 路径回归：50 个节点、2,500 对起终点，和原实现比较距离及完整路径，包括同分选路、不可达、FIFO 淘汰、加边失效、跨地图隔离。
- 服务节点回归：正式地图中中介／展会地点，与原有全量门口净空扫描逐项比较。
- 测试夹具修正单独记录，不计作修复玩家可见 Bug：旧晚餐测试只改时钟并等待自动结束，而当前实际流程需要正常排班、入座、点击结束用餐；赛车 NPC 上班不应受玩家登记条件限制；直播工作与线下门店营业分别判断；旧长途测试点位在地图缩小后已变成步行范围；客流预期补上既有在店加成及街道需求归一化；商圈说明按现有详情按钮进入检查。

## 测量边界与后续验收

旧巡检从 `EditorApplication.update` 调用 `Step`。本轮另加 `-PlayerLoop`，在 Unity 的正常 Update 循环推进，并单独记录引擎线程时间，避免把测试驱动误当作游戏瓶颈。两种驱动结果分别归档，不混成同一组前后百分比。

花园单场诊断（`playerloop-diagnostic/20261127-223801`）平均 147.25 FPS、P99 9.11 毫秒；最慢帧 45.16 毫秒，其中视图同步 35.33 毫秒。CPU 主线程帧计时 P99 7.38 毫秒、渲染线程 5.48、GPU 6.19；各列百分位不是同一帧，不能相加，也不能因此直接宣称发布包稳定达标。

这仍是编辑器测量。尚未覆盖发布包、所有天气、连续全城移动、后期多店重负载。未经本次明确打包授权，不生成发布包。剩余目标是普通游玩与加速中都减少超过 8.33 毫秒的慢帧，保留画质和玩法结果。

人物预备有明确成本：本轮进城加载总耗时约 6.35 秒，其中 `loading_people` 约 2.59 秒；预备前完整轮次分别约 3.79 秒、0.13 秒。城郊采样时 Unity 总分配读数约 1,804 MiB，预备前约 1,663 MiB。这是用较长的首次加载及共享资源常驻，换取游玩中减少首次出场卡顿；不是零成本优化，也不是独立的发布包内存测试。

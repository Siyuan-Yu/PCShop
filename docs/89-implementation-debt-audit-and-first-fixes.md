# 全局实现债务盘点与第一批修正（2026-11-07）

## 范围与结论

以第88篇归档、Git `97f8147` 为起点，对运行时代码做全局静态检索、规模统计和重点调用链核读。本轮修改后共339个C#文件、约6.1万行，Core 182个、Game 157个；源码清单见[范围索引](validation/89-source-inventory.json)。重点核读车辆/车库/员工运力、财务/存档、任务与晋升、房产、直播展会、托管经营及UI刷新。没有逐行验证所有玩法，也不能把“未搜到TODO”视为没有问题。

目前不是“全是假实现”：采购会实际扣款扣库存，员工运输占用具体车辆，展会真实转移展品并结算，品牌合约、房产和车位也有实际状态与持久化。但存在三类问题：会直接影响正确性的临时补丁；能运行但耦合很强的架构；尚未制作或有意简化的玩法。三者分别列出，不把所有硬编码数值或简易玩法都当作bug。

## 本轮已修正

| 项目 | 原问题及影响 | 本轮处理 |
| --- | --- | --- |
| 车辆有两份所有权数据 | `_owned`只记类型数量，`_garage`记具体车辆；`Garage`等查询调用`SyncGarage`按数量创建默认车型或删除末尾车辆。读取界面就可能修改车辆，新增车型/购买入口容易丢改装和编号 | 删除运行时数量副本及`SyncGarage`；买卖、收车、撤回展位只更新具体车辆。数量、魅力、养护、通勤与员工可用数量均从车辆实例推导；查询不再增删资产 |
| 扣押又有两份数据 | 总扣押数和每台车的`Impounded`并存，漂移时可能付了赎金却找不到对应车 | 只保留逐车扣押状态，统计直接派生。存档中的旧汇总字段仅作为派生输出；无明细的早期数据只在读取边界导入一次 |
| 车辆分类混用 | 原`ClassOf`把所有非电驴/三轮都归为四轮，未知类型也会被当成轿车；外形、赛车资格、车行分类共用一个数字 | 一张分类定义明确默认车型、所属车行、外形、赛车类别和销售类别。货车赛车类别为-1，赛场/车库/车产使用`RaceClass`，外形与二手四轮展示仍使用外形类别；未知类型不再默认为轿车 |
| 分区规则散落数组 | 圈数、胜场、营业时间、车位租售价、二手车源上限分散多处，部分读取每次新建数组 | 集中为`RacingTierRules`，赛场、车位和二手车源共用；本轮不改变现有平衡数值。增设片区仍需配置地图与入口，不宣称已成为任意数量片区的系统 |
| 报废车辆卖出异常 | 车况归零时仍调用只允许正数的入账接口；车先删了，再因零金额抛异常 | 残值统一计算并限制车况范围；零残值回收不会创建非法收入或抛异常，有残值照常入账 |
| 直供尾款漏门店归属 | 赊购债务没有门店ID，手动还款与强制扣款都只写总账，门店七日支出漏掉尾款 | 债务保留`ShopId`及`OrderId`；手动、自动、逾期强扣共用归属和结清事件ID，防止改店后记错或重复扣同笔款。没有来源的历史债务不猜到当前店 |
| 历史展会费用被现价重算 | UI用当前摊位/海报报价计算往届费用；今后调价会改掉旧结算差额 | 核心层新增`GetExpoFinance`，读取本届实际付款事件及逐商品销售，界面只展示报告；费用记录不完整时明确不计算差额，不拿今天报价补历史 |
| 文字控制业务 | 整机交付任务通过“备注不含展示机”完成；直供任务看中文备注前缀；房产占用用租户文字等于“空置”判断 | 两项任务使用成功操作已有的持久化事件标记；房产报价加入`HasTenant`，产权用途由状态判断。改备注、改文案不会改变这些规则 |
| 车辆账目进入“历史未归属” | 购车、售车、赛车报名/奖金、整备及日养护未注册默认业务分类 | 车辆买卖归资产投资，赛事、交通、改装整备归个人生活；显式门店归属仍优先，员工业务不被这层默认规则覆盖 |

## 不应误判为脏实现的部分

- “临时存放”是仓储玩法名称，不是临时程序；不能搜索到“临时”就删除。
- `placeholder`可能是文本输入提示或无店铺时的合法空状态，不等于伪造经营。
- 店铺模拟和升级目录的“数值占位”注释说明平衡还需试玩，不代表付款/效果没有接入。
- 核心层与Unity表现层有程序集区分；账本已有业务归属、来源事件去重和存读档，不能一概重写。
- Windows存档使用临时文件＋原子替换＋备份，并非无保护地直接覆盖。WebGL路径单独处理，仍需发行平台验证。
- 编辑器验收档、调试凭据有明确宏边界，测试内容不是自动送给正式新游戏；保留对开发有用的验收入口。
- 场景用代码生成低多边形几何是当前资源策略。应看组件职责、复用和生命周期，而不是因没有手工Prefab就判成临时实现。

- **11–20 是下一批**。先核对各项当前做了什么、正文声称发生了什么、玩家可以怎样选择。给出具体改法和数值，确认后再改进游戏。[第 11 项「网上有人说你家卖翻新货」](100-random-event-details.md#11--网上有人说你家卖翻新货)是下一批的起点，第 12 项是「发传单的上门了」。第 12 项是典型的待改内容，结果写了次日有学生进店，当前脚本只扣钱、加名望和显示结果。
- **21–30、31–40……121–126** 依编号继续。第 108 项周末搬货已经接入实际工作时长，保留这项已落地的行为，轮到该编号时再整体检查。第 102 项保留空号。当前没有为后续批次确认新规则。
- [全部事件现状](100-random-event-details.md)逐项列出正文、触发条件、选项、效果和概率分支。它是接手时的基线。后续改一批，就更新对应条目、核对状态和本页的下一批起点。

## 换电脑后怎么接着做

新电脑已有仓库时，在仓库目录运行 `git pull --ff-only origin main`。首次下载可用下面的命令。如果仓库已有本机改动，先保留这些改动再同步。

```powershell
git clone https://github.com/Siyuan-Yu/PCShop.git PCShop
cd PCShop
git status --short --branch
git log -3 --oneline
```

用 Unity Hub 打开含 `Assets` 和 `ProjectSettings` 的目录。编辑器版本是 **2022.3.6f1**，主场景是 `Assets/Scenes/Main.unity`。继续改事件用 GitHub 上的 Unity 源码。批量验收每批会准备独立测试场景，因此换电脑继续该批次无需复制原机器的个人存档。

## 每批的做法

1. **先读当前行为。** 通过[编号索引](98-random-event-index.md#事件目录)找到 ID，读[现状清单](100-random-event-details.md)和实际代码。记录场景、触发条件、选项、前置要求、即刻效果、延迟效果、失败后果。核对实际效果与文字，尤其留意现金账、指定门店、人物和时间。
2. **先讨论再改。** 每项列清「现在」「拟改选项」「实际结果」「相关属性与数值」，指出需要玩家确认的门槛或平衡。已有决定沿用，例如 01 的有效魅力门槛 45、起始成功率 35%、每点加 1 个百分点。其他事件按情境选魅力、智力、技能、交情、准备条件或经营规模。
3. **接入实际系统。** 顾客应真实到店，订单应扣真实库存并进对应门店账，送货、打工和赴约应经过游戏时间，关系变化落到实际人物。涉及后来才发生的动作，记录目标和到期时间，确认跨日、关闭窗口和重新加载后的结算行为，以及重复触发会怎样。保留合理的拒绝或延后选择，明确按钮成本和禁用原因。
4. **就地维护配置和代码。** 简单条件、文案和现有脚本效果改 `Assets/Resources/Data/events.json`。需要绑定真实店铺、改变库存或排入后续流程时，沿用 `EventCatalog.cs` 和 `GameSession.Events.cs` 的注册和绑定方式。周维成事件在 `NpcEvents.cs`。脚本运行方式见[配置说明](events-json.md)。保持事件 ID 和目录相对顺序，验收编号目前由目录顺序加 102 空号计算。合并或新增时同步核对编号映射和相关检查。
5. **检查并记录。** Unity 菜单「PCShop → 事件 → 校验 events.json」校验配置。按当前协作约定，代码修改以 Unity 编译为常规检查。用户要求实玩时，在编辑器内打开「作弊 → 随机事件批量验收」，下一批选 **11–20**。处理一个事件并关闭结算后会到下一项。碰到工作或约会等延迟效果时，让时间走到该动作完成再核对实际结果；记录工具报告的跳过项及原因。验收可以测试分支和结果，自然抽取条件还要单独对照配置。更新此页和事件详情后提交并推送。

# 随机事件逐项优化交接

## 目前做到哪里

这项工作是把已经存在的百余个随机事件逐个改得更真实，让选择和角色成长有实际影响。当前随机池有 **123 项**，批量验收编号为 **01–126**。102 已并入 09，125、126 是独立触发的社交和救急事件。城郊升社区、社区升公园、公园升花园以及许星澜的首次赛车引导属于独立主线。

- **01–10 已完成改造**。初版基准提交为 `4994c27`，本轮归档包含后续复核调整。现行规则见[前 10 项](98-random-event-index.md#前-10-项玩法)。
- **01、04、05、06 的复核调整已实现**。按属性判定的随机事件统一使用达标后随点数增加的成功率，详见[配置说明](events-json.md#掷骰)。
- **11–20 已改进游戏**。包括 ¥1,000 来源核验、¥200 传单推广、四个片区医院、真实住址和做客邀请，以及按店型交付的两种转介绍订单。[11–20 的规则](100-random-event-details.md#11--网上有人说你家卖翻新货)。
- **21–30 已实现**。采购与借款按到期时间结算，车友聚会与正赛写入日程，整备改实际车况，收藏车接入单圈试驾。[21–30 的规则](100-random-event-details.md#21--周维成出清库存)。
- **31–40 是下一批**，从 31「骑手的小挑战」开始。第 108 项周末搬货已经接入实际工作时长，轮到该编号时再整体检查。第 102 项保留空号。
- [全部事件现状](100-random-event-details.md)逐项列出正文、触发条件、选项、效果和概率分支。它是接手时的基线。后续改一批，就更新对应条目、核对状态和本页的下一批起点。

## 随机抽取与结算

- 游戏时间跨过 11:00、15:00、20:00 时检查。从开局计日第 2 天开始，要求有自营店、随机事件已开启、没有待选择事件，且玩家清醒、游戏仍在进行。品牌展会专属流程期间暂停随机抽取。第 2–13 天每时段 20%，第 14 天起为 40%。当日最多 3 项，包含当天的连续 7 天最多 10 项。
- 时段通过后检查事件的起止天数、按 ID 计算的冷却、店铺或人物等触发条件、独立触发概率，再按权重抽取。赛车组还要求完成城郊首跑。绑定出实际待选择事件才计入随机池频次。活动、剧情与后续结算有自己的入口。
- 有属性系数的掷骰在任一相关数值低于门槛时为 0%。达标后从基础值起算，超出的点数按系数增加。常用门槛为有效魅力 45、智力 50、交情 35，个别事件有独立门槛。按数值判定的成功率与事件抽取概率各自计算。[掷骰配置](events-json.md#掷骰)
- 01 的复查、02 的留货和到访、07 的失物交还、09 和 25 的借款、12 的推广、19 的饭后谈租及 30 的赛后邀约都有各自的后续处理。固定还款在到期日自动入账，25 在到期时按借出时记录的概率判定。借款逾期和赛后邀约在玩家空闲时弹出。
- 125 在首单后由空闲检查发起，优先找交情至少 30 的熟人，现金门槛 ¥50,000。126 在连续负现金达到条件时直接入账 ¥3,000，凭一次性标记防重复。正式区域晋升、赛车入门、新闻、品牌展会与普通活动由各自系统记录。

## 换电脑后怎么接着做

新电脑已有仓库时，在仓库目录运行 `git pull --ff-only origin main`。首次下载可用下面的命令。如果仓库已有本机改动，先保留这些改动再同步。

```powershell
git clone https://github.com/Siyuan-Yu/PCShop.git PCShop
cd PCShop
git status --short --branch
git log -3 --oneline
```

用 Unity Hub 打开含 `Assets` 和 `ProjectSettings` 的目录。编辑器版本是 **2022.3.6f1**，主场景是 `Assets/Scenes/Main.unity`。继续改事件用 GitHub 上的 Unity 源码。批量验收每批会准备独立测试场景，因此换电脑继续该批次无需复制原机器的个人存档。

## 每批的做法

1. **先读当前行为。** 通过[编号索引](98-random-event-index.md#事件目录)找到 ID，读[现状清单](100-random-event-details.md)和实际代码。记录场景、触发条件、选项、前置要求、即刻效果、延迟效果、失败后果。核对实际效果与文字，尤其留意现金账、指定门店、人物和时间。
2. **先讨论再改。** 每项列清「现在」「拟改选项」「实际结果」「相关属性与数值」，指出需要玩家确认的门槛或平衡。已有决定沿用，例如 01 的有效魅力门槛 45、起始成功率 35%、每点加 1 个百分点。其他事件按情境选魅力、智力、技能、交情、准备条件或经营规模。
3. **接入实际系统。** 顾客应真实到店，订单应扣真实库存并进对应门店账，送货、打工和赴约应经过游戏时间，关系变化落到实际人物。涉及后来才发生的动作，记录目标和到期时间，确认跨日、关闭窗口和重新加载后的结算行为，以及重复触发会怎样。保留合理的拒绝或延后选择，明确按钮成本和禁用原因。
4. **维护配置和代码。** 简单条件、文案和现有脚本效果改 `Assets/Resources/Data/events.json`。复杂业务沿用 `EventCatalog.cs` 和 `GameSession.Events.cs` 的注册与绑定。周维成在 `NpcEvents.cs` 注册，实际交易在 `GameSession.EventDeals.cs`。保持事件 ID 与目录相对顺序，合并或新增时核对验收映射。[配置说明](events-json.md)
5. **验收并记录。** Unity 菜单「PCShop → 事件 → 校验 events.json」检查配置。在编辑器内打开「作弊 → 随机事件批量验收」，下一批选 **31–40**。处理当前事件、关闭结算后会到下一项。需要数小时或跨日的结果，可停下批次、在测试档里继续验证对应结算。记录跳过项及原因。批量触发用于核对事件分支，自然抽取条件要另测。将规则、验证状态和未完成项写入文档后提交并推送。

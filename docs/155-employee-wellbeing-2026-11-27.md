# 员工满意度、请求与离职交接实施记录

2026 年 11 月 27 日 · Unity 2022.3.6f1 · 当前开发分支 `art/experiment`

本轮把已讨论的员工满意度落实到门店、公司和居家工作台。门店员工从首次入职就有满意度，注册公司不是解锁条件；个人员工转入公司、门店与部门之间调动时保留同一个员工记录。公司股权、接管和场景美术不是本轮修改范围。

后续同日接入的[公司治理与交接](156-company-equity-and-control-2026-11-27.md)继续使用本篇员工状态。公司易主保留满意度和待办，新管理层接手非留任门店的人事处理；工作台只把玩家有权管理的员工请求列为个人待办。工资账户归属以第 156 篇为准。

## 满意度怎样结算

满意度与精力各为 0–100，入职满意度 65、精力 100。它们独立于 NPC 好感度和玩家精力。工资、在岗、休息和任务均复用原有员工与工资系统。

- 只给真实执行且已结束的班次结算满意度，不按点击次数、日历翻页或菜单停留结算。同一工资工作日最多结算一次。旧工资历史不补算满意度。
- 班次目标值从 75 起。每班向目标渐变 20%，向上取整且最多变化 3 点，最后限制在 0–100。反馈列出本班实际原因；最近六次记录随档保存。
- 薪资期望以入职基础日薪为基准。普通岗位 1 倍、部门负责人 1.15 倍、公司任命店长 1.25 倍。升职后薪资不足会产生压力；已经给出的加薪不会反过来抬高入职基准。
- 实际工时超过 600 分钟算长班；连续长班、两班休息不足、低精力、持续不适岗和反复调岗降低目标。8 小时以内的实际班次有正向作用。
- 首版负荷检测覆盖收银排队和宠物照护超负荷。其他行业尚未单独设置负荷指标，不能把它理解为所有岗位都已有独立压力模型。

| 因素 | 首版计算 |
| --- | --- |
| 日薪不足岗位期望 | 目标扣 `min(30, (1−实际日薪/岗位期望)×70)` |
| 日薪至少高于期望 15% | 目标加 5 |
| 长班 | 每超出一小时向上取整扣 4，再扣连续长班数×3（该项最多 15） |
| 实际班次不超过 8 小时 | 目标加 5 |
| 两班间休息不足 10 小时 | 每不足半小时扣 1，最多 18 |
| 结算时精力低于 30 | 目标扣 10 |
| 排队／照护超负荷覆盖至少三分之一工时 | 目标扣 8 |
| 连续三班主要在明显不适合的岗位 | 目标扣 8 |
| 一班内发生至少两次岗位变化 | 目标扣 4 |
| 员工请求逾期 | 每多一个实际班次扣 5，最多 25；明确拒绝再扣 5 |
| 请求实际兑现 | 标记兑现、撤回离职预告，班次目标至少达到当前满意度加 3；仍遵守单班渐变上限 |
| 已批准带薪休假完成 | 直接恢复 3 点；同一次休假不重复奖励 |

这些数值是当前实现参数，尚未经过长线经济平衡。不能把文档中的计算规则视为已完成自动测试或长期模拟。

精力按实际工作分钟下降、非工作分钟恢复。每分钟工作消耗为 `0.085−体能×0.0003`（体能限制为 0–100），休息每分钟恢复 0.10，最后限制到 0–100。员工在调岗、休假时保留精力。

满意度分段为：80 以上「满意」、60–79「稳定」、40–59「不满」、40 以下「需处理」。基础工作效率依次为 105%、100%、97%、94%；精力低于 30 时再乘 95%，总效率最低 90%。已经接入收银、装机、餐饮操作、销售加成、模型制作、二手修复和部门项目。按整分钟结算的短任务会受分钟取整影响；部门项目保留小数工时，避免每分钟取整丢失效率差。

## 请求与离职

满意度低于 60、至少完成两个真实班次，且没有未解决请求时，员工可根据实际问题提出请求。顺序是薪资不足、低精力或休息不足、连续长班、持续不适岗、持续负荷。当前岗位适配低于 40，且同店可用岗位适配至少高 25，才提出换岗建议，避免每个人不断要求换工作。

请求给出三个实际班次的处理期。可推迟一次，增加两个实际班次；拒绝或超期会继续影响之后的结算。同意请求仅记录安排，不能刷即时奖励。加薪在新工资快照下工作、短班实际执行、换岗后到目标岗位工作、已批准的休假完成，才算兑现。玩家不点同意但真正满足条件，也可以兑现。

满意度连续三个实际班次低于 30，且有逾期未解决请求时，才发离职预告。预告给出三个后续实际班次；请求兑现或满意度恢复到至少 40 时撤回。到期仍未改善时结束雇佣，先结清已发生的基础工资及加班费，保留历史工资记录，腾出原岗位。员工或采购货物尚在交接途中、已承担展会工作时等待交接完成。

**超编仍只提示，不自动裁员。** 离职依据持续待遇问题与已通知的预告，不按编制直接清人。带薪休假保留职位，不自动塞替班人员。

## 工资、存档与兼容

1. 沿用原基础工资的每日结算周期、600 分钟后的加班规则及账目归属。本轮没有新增奖金系统、欠薪选择或独立公司钱包扣薪规则。
2. 在当前班次中调薪，先固定本班工资，再保存待生效日薪。预估下班次工资与加班费分别计算，薪资差额不计作加班费。
3. 休假从下一可用班次开始，正常恢复精力，不参与在岗工作与部门项目。一天按 24 小时计算，能覆盖跨午夜班次；采购与展会任务未处理完时不能批准新休假。
4. 保存员工满意度、精力、入职基准工资、待执行日薪、休假、实际班次数、请求、预告和最近六次变化。工资记录保存已观测工时与满意度结算标记；部门项目保存小数工时。
5. 保存时写入显式标记 `hasEmployeeWellbeing`，避免 Unity `JsonUtility` 把旧档缺失的嵌套对象当成有效零值状态。旧档没有该标记时，从当前游戏时间初始化为满意度 65、精力 100，不追扣过去长班、不在加载时直接触发离职。正式存档结构使用原保存入口，嵌套请求和历史均做深拷贝。

## 实机画面与验证边界

[十张 Unity 原帧与页面文字](art-direction/implemented/employee-wellbeing-20261127/index.html)覆盖个人员工、三种同屏操作、离职预告、同意后等待执行、公司名册和请求筛选、公司总览、全屏工作台。截图使用隔离预览工程和临时展示员工，不读取或修改玩家正式存档；满意度、请求和预告是专门准备的展示状态。图中人物名称为界面样本，头像沿用现有素材。

已进行 Unity 脚本编译和界面逐图检查。同意调班这一帧实际调用 `RespondEmployeeRequest`：请求变为待执行，满意度仍为 48。其余准备状态不是对多日结算、保存重载或离职完整路径的运行验证。

本轮未运行自动测试、未做长线数值模拟、未生成发布包、未提交或上传。下一轮获得测试指示后，优先覆盖：旧档迁移；跨午夜调薪调班；带薪休假与替班；调岗后实际兑现；预告撤回／到期；人员与货物分开回程时的离职交接；工资和满意度保存重载的幂等性。

## 复拍与换机

[复拍入口](../tools/employee-wellbeing/EmployeeWellbeingCapture.cs)放在 `tools`，不随正式游戏编译。需要复拍时，将它复制到隔离预览项目的 `Assets/Editor`，同步最新 `Assets/Scripts`，设置绝对路径环境变量 `PCSHOP_EMPLOYEE_OUTPUT`，再调用 `EmployeeWellbeingCapture.Run`。运行时生成空场景，准备临时展示状态，导出 1920×1080 PNG 与活跃 UI 文字后退出。

Unity 命令参数为 `-batchmode -projectPath <预览工程> -executeMethod EmployeeWellbeingCapture.Run -logFile <日志>`。不要给该次调用添加 `-quit`，入口要等待进入 Play Mode。成功日志标记为 `EMPLOYEE_WELLBEING_UI_CAPTURE_DONE`。这不是自动测试入口；只有重新授权运行测试后才应另行安排业务验证。

本轮继续在既有美术分支 `art/experiment` 工作；猫狗与商品图标的前序本地修改也保留在工作区。后续提交或换机须一并保留，不要只挑新员工文件。上传与打包需新的明确指示。
